# M0.2 Identity and Tenant Isolation (initial implementation)

## Implemented
- Flyway V2 identity/role tables and RLS on tenant-scoped company, branch and audit tables.
- DB-backed Basic authentication with BCrypt password verification.
- Authenticated `GET /api/v1/me`, returning the server-authenticated tenant ID and roles.
- TenantJdbcExecutor sets a transaction-local `app.tenant_id` context.
- All other business routes remain closed by default.

## Important incomplete gates (DO NOT DEPLOY TO PRODUCTION)
- No safe self-service provisioning, invitation or password reset yet.
- No login rate limiting, MFA, session revocation or OIDC.
- No role-based business endpoint policies; all business endpoints remain denied.
- Migrations and application currently share DB credentials in the local scaffold. Production must use a separate non-owner, non-BYPASSRLS application role.
- No PostgreSQL/Testcontainers integration verification was run in this artifact environment. RLS must be tested with two tenants plus connection reuse and rollback before opening CRUD endpoints.
- Global `auth_identity` lookup must remain restricted to the authentication service only; never expose as tenant CRUD.

## Manual test plan
1. Run Flyway through application startup using `./scripts/start-local.sh`.
2. Check V1 and V2 migration records using `flyway_schema_history`.
3. Create a tenant and BCrypt-hashed test identity in a *local-only* database (do not use plaintext passwords or commit credentials).
4. Confirm `GET /api/v1/me` requires valid Basic credentials; unauthenticated requests return 401.
5. Confirm `POST /api/v1/me` and all other `/api/*` requests are rejected.
6. In a transaction set `app.tenant_id` using `set_config(..., true)` and confirm company RLS only returns that tenant's rows.
7. Confirm no tenant setting produces zero rows and that transaction reuse does not leak the setting.
8. Repeat isolation using a restricted production-equivalent DB role and Testcontainers.
