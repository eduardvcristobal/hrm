# M0.3.4.7 — MFA key rotation and recovery (draft procedure)

**Status: not production certified.** This documents operational constraints; MFA factor recovery/reset endpoints are not enabled.

## Key configuration
- `HRM_MFA_ENCRYPTION_KEY`: active 32-byte AES key, base64-encoded, supplied via approved secret manager.
- `HRM_MFA_PREVIOUS_ENCRYPTION_KEY`: optional previous 32-byte key **only during rotation**.
- Only encrypted `v1`/`v2` AES-GCM envelopes are accepted. There is no plaintext fallback. Never commit production key material.
- The envelope does not yet encode a key identifier. The previous-key slot only supports one transition; rotate factors before another rotation.

## Rotation runbook
1. Freeze additional key rotations and take a verified encrypted backup with both old key metadata and recovery procedures.
2. Provision a fresh random key in a secret manager, retain the old key in the previous-key slot, and deploy together to all replicas.
3. Verify enrolled factors can still be used and new enrollments use the active key. Watch authentication error metrics.
4. **Do not remove the previous key until a separate audited re-encryption job has rewritten every old-key factor**. This job is not yet shipped.
5. Test recovery on a replica and confirm no factors still require the previous key before removing it.
6. In case of a failed rotation, restore the prior key configuration under change control; never reset factors automatically.

## Recovery requirements (not yet implemented)
- No self-service bypass or password-only removal of MFA; password reset must not disable MFA.
- Require verified identity, an approved out-of-band channel, recorded case ID, and independent administrator approval.
- Revoke all API tokens before supervised MFA replacement. Retain audit evidence and alert the account owner.
- Require a newly verified authenticator; do not provide universal recovery codes.
- Add automated negative tests for bypass attempts, replay, concurrency and cross-tenant recovery.

## Acceptance blockers
- Key identifiers and a dedicated audited online/offline re-encryption job, with backups and rollback drill
- Secret-manager key provisioning, least privilege and rotation evidence
- Two-person recovery approval design and implementation; operational acceptance
- Integration tests under the restricted runtime database user
